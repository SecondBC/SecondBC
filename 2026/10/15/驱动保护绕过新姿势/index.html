驱动保护绕过新姿势
发表于 2026-10-15 | 更新于 2026-10-15
Lab
Bin

这篇是为了回应：驱动obcallback反附加的一次尝试【Second_BC の BloG】 的最新的解决方法；

隔了一年没更新是因为忙事情去了（

之前我们提到过，使用OB回调的方法进行进程打开时的修改操作的这种方法，非常不稳定，会掉线，附加会脱落；

目前的版本也不支持这种姿势绕过了，一进入游戏进程就会直接被检测到异常，弹窗报错然后直接游戏进程死掉；

同时之前的劫持驱动文件的方法非常的不优雅，而且目前版本也不支持这种低级绕过姿势；

针对这些个问题有了今天的这个补充篇；

环境和时间铺垫：

最新测试结果可行，时间节点为 2026.7.30 以前，往后没有进行过测试，不保证该方法仍然有效；

测试平台为 win10 旗舰版，win11肯定干不起，除非你能在win11上把过期签名的驱动跑起来，或者其他手段能给win11签名绕过或者正版签名；

最好不要使用虚拟机，现在的版本对虚拟机有检测，除非你有信息能绕过虚拟机检测；

由于过去了一段时间我才开始写这篇内容，所以有些实验结论我就直接给了，实验作证截图确实是找不到了（

初步实验猜想

第一处疑点

之前的篇子里提到过，保护驱动主要做的事情进行降权，降权是什么意思呢，如何降的呢？

降权的本质是在保护驱动开启的OB回调里面，检测当每次打开的进程是目标游戏进程的时候，就会让打开句柄的权限降低；

主要就是把可写的权限位给抹除了；

举个例子，当你编写程序使用 OpenProcess API 的时候，第一个参数一般我们会填入 PROCESS_ALL_ACCESS ，意思是以可读可写的方式打开这个文件或者进程句柄；

但经过我的测试，使用R3编程的控制台程序，直接打开这个游戏的进程句柄，返回的句柄通过 NtQueryObject 查询句柄访问权限的掩码，可以发现读写的权限都被抹除了；

这就是为什么使用CE打开进程后，地址出现问号，进程图标加载不出来的原因，因为CE也是使用 OpenProcess 这个API打开进程句柄，并通过后续的一系列API对句柄进行使用以读取内存地址，查询地址空间等操作，比如：ReadProcessMemory，WriteProcessMemory，等；

之前那个篇子中使用的思路是我们自己也写一组OB回调，分别放在OB回调的开始和结束（用优先级设定），针对目标游戏进程句柄的权限进行恢复操作，在这样的一个恢复过程后，CE确实能够看到进程图标，并且能够访问内存空间，这本身没有问题；但保护驱动做了什么措施，导致这样的姿势绕过以后会被检测到，导致游戏死掉；

我推测是保护驱动或者是游戏模块内某块区域持续检查（或者称呼为管理）目标进程被打开的句柄；检查这些被打开的句柄的权限是否异常，如果异常，就杀掉游戏进程，所以我们不能想着去改动打开的游戏进程句柄的权限了；（目前的版本就算使用SYSTEM级权限的CE也会报错闪退，或者根本打不开）

第二处疑点

我使用 PChunter 这玩意儿对游戏进程进行模块查看，发现能够正常返回游戏的每一个模块的基址，我就很好奇，为什么 PChunter 能看到被限制权限的游戏进程的模块基址，而CE不行；

同时，用 PChunter 访问了游戏进程的模块基址后，游戏并没有出现异常或者报错，或者闪退，非常稳定；

于是我开始思考他们两者的差异，即：

PChunter 会挂载驱动，它应该是通过驱动内的手段进行的内核级别的内存扫描；

而CE这东西，直接就是用的R3下的OpenProcess和其他API来操作的，这肯定会受限制；

思路

所以有了想法，即不改变CE打开游戏进程句柄的逻辑，但是改变CE读内存和写内存的逻辑；

至于调试器会不会受影响，我的答案是肯定会，但是我们仍然有CE的dbvm可以用，dbvm调试模式也是走的驱动层面，这条路可行；

由于我们只改变了内存读写逻辑，而没给操作的进程句柄提权；所以线程级操作肯定干不起，比如调试中的线程断点是没有效果的，但是仍然可以选择使用dbvm调试，打断点到对应位置，依旧会正常停下；

结论

这种思路打开了局面，经过我的测试，虽然CE的某些功能受到了限制，但是我们的主要操作已经绕过了，大部分的逆向操作都能直接进行工作，比如：扫描内存，扫描指针，查找是什么访问/改写了这个地址，打断点，单步调试，dump内存等等；这些操作不会触发反调试（因为使用了dbvm），也不会触发异常报错（没有动核心检测点：句柄）；

经过我的测试我可以得出一个很明显的结论：这款游戏的保护模块根本没有强检测CE这个程序（但是检测了虚拟机），它并不像腾讯的一些驱动保护会查CE进程的特征；它也没有设置很多内核钩子去监控比如驱动链表，异常驱动模块，驱动回调，你建的异常OB回调等等；有反调试，但对于dbvm的CE来说相当于没有；主要还是针对于自身模块和句柄的权限维持；

接下来就是我写的源代码了，总共有三个模块：

一个是SYS驱动模块，主要是实现内核级内存查询，内存写，内存读；

第二个是DLL模块，用于进行和驱动设备的交互，接口的作用，把CE函数调用约定给到驱动，再由驱动返回CE函数应该得到的返回结果；并在附加到CE进程后对CE的关键函数进行HOOK，替换为这些接口函数，使CE每次调用关键函数走驱动实现；

第三个就是注入器了，把编译好的DLL注入到CE进程，改变CE的执行逻辑，使其绕过检测，正常工作；

值得说明的是，如果游戏的保护驱动检测力度更狠，比如检测到了我上面提到的一些内核级的内容；那么就要考虑其他绕过姿势了，详见：驱动设备引入-Windows驱动编程二【Second_BC の BloG】 ；

三个模块是让 AI 辅助去写的，风格不像之前一样保留大多数注释，但是思路就是上述提到的三个模块的设计思路；

虽然AI时代，AI确实能够代替老时代的残党进行大量的脑力工作和枯燥的逆向过程和漏洞挖掘过程，极大优化分析时间（CTF已死）；但是这些绕过思路，对抗思路，长时间内，是AI不可能告诉你的，也是风控严格的AI不会去做的；除非你很吊，非常有刀，自己训练一个属于自己的还算聪明的大模型语言，那我没话说了，你随意；或者使用 agent 阵列组或者设计 harness 控制一些风控较低的但是笨的AI，让高级别的更聪明的AI给他们布置任务和写提示词来实现思路的产生或是exp的编写，也行；

所以往后的学习道路，Agent 是肯定躲不过去的，必须学的内容；老时代的课程也得看，还是得让自己变得更有思路才行；
